# AGENTS.md

Instructions for coding agents (Codex, Devin, Claude Code, or otherwise) working in this repo. If you're drawing or animating a scene rather than working on the library itself, read the "Drawing with sketchling" section below — it's the same reference as `.claude/skills/sketchling/SKILL.md` and `.agents/skills/sketchling/SKILL.md`, kept here too since not every agent reads a skills directory.

## Working on the library

- `npm run build` compiles TypeScript (`tsc -p tsconfig.json`) — run it before any `sketchling render` call picks up source changes, since the CLI imports the built `dist/`, not `src/` directly.
- `npm test` builds then runs the unit tests (`node --test test/*.test.mjs`): deterministic core math (geometry, IK, the gait zero-slide contract, the Tier 0 linter) and the agent manifest contract. `npm run lint` runs ESLint. Both run in CI (`.github/workflows/ci.yml`) along with a render smoke test and a two-render byte-identical determinism check. Unit tests cover what's cheaply provable in Node — visual changes still need verification by rendering a scene and looking at the actual output (see "Verifying your own work" below).
- Core (`src/core/`) has no DOM dependency on purpose — it needs to run cheaply in plain Node for the Tier 0 linter and for `sketch.scene()`/`sketch.film()` construction. Don't introduce a DOM/browser dependency there; that layer belongs in `src/render/`.
- `src/render/renderer.ts` is the animation engine's spine (mount/mountFilm, the scene builder, the per-op animation dispatch); the subsystems it coordinates live beside it, one module each — `drawon.ts` (mask-based reveal), `boil.ts` (line boil), `camera.ts`/`springs.ts`/`connectors.ts`/`particles.ts` (the per-seek live systems, in that postSeek order), `mesh3d.ts`/`limb.ts` (per-tick redraw nodes), `morph.ts`, `textures.ts`, `background.ts`, with shared internal types/ids in `internal.ts` and node-lookup helpers in `scene-query.ts`. This layer is the most load-bearing code in the repo and the trickiest to get right blind; changes here deserve an actual rendered check at a genuinely mid-motion timestamp, not just a build check (see the modules' own comments for several non-obvious GSAP behaviors already found the hard way). Renders are deterministic — the same scene at the same `--at` is byte-identical — so `cmp` against a pre-change render is a real verification tool for refactors.
- `examples/` are vocabulary demos (one concept each); `examples/story/` is a narrative sequence; `examples/launch/` is launch-video-specific source, not meant as a general example. Don't mix these purposes into one file.
- `site/` is the in-browser playground (deployed to GitHub Pages): `npm run build:site` bundles it, `npm run site` serves it locally, `npm run test:site` drives it through headless Chromium. It reuses `mountRenderable` rather than reimplementing any rendering, so a renderer change lands there too — see `site/README.md`, including what the page genuinely can't do (`texture: "pixel"`, `sketch.sound()`). Presets are real scene files in `site/presets/`, checkable with the CLI like any other example.

## Drawing with sketchling

A hand-drawn illustration and animation vocabulary, rendered through rough.js + GSAP. Like Manim: a toolbox of primitives and animations, not a pipeline. Nothing below is mandatory — pick whatever combination of tools serves what you're actually drawing. The defaults (pacing, easing, single-pen scheduling) exist because they usually look good, not because anything enforces them; override any of them whenever the scene wants something different.

### Setup

```ts
import { sketch } from "sketchling"; // or "../src/index.js" if working inside this repo, pre-publish
const scene = sketch.scene({ width: 480, height: 420, background: "#7096c6", seed: "my-scene" });
// ... build nodes, add them, animate them ...
export default scene;
```

`width`/`height` are the world. Pass `viewport: { width, height }` too when the world is bigger than one screen and a `scene.camera()` (below) pans/zooms within it; omit it and the output frame is just the whole world, same as every scene not using a camera.

`sketch.scene(...)` also takes `look` and `texture` (see "Look and texture" below) — decide the register deliberately before drawing a single primitive, not by default. Every example this repo ships that a fresh agent is likely to see first (`examples/story/lantern-maker.ts`, most of `examples/showcase/`) happens to use `look: "ink"` with a restrained, muted-palette register — that's this corpus's own bias toward one story, not a technical default or a recommendation. `"flat"` (crisp, ligne-claire/Tintin-adjacent), `"clay"` (stop-motion cadence), `"lit3d"`/`"toon3d"` (real lit 3D), and `texture: "pixel"`/`"watercolor"`/`"grain"` are equally real, equally finished registers — the same authored scene, painted differently, at zero extra authoring cost. Two different scenes about entirely different subjects that both end up ink-on-parchment isn't a coincidence this library forces; it's an unexamined default worth actively pushing against.

```
sketchling render scene.ts --out preview.png            # settled end state
sketchling render scene.ts --out mid.png --at 0.6        # a specific timeline moment
sketchling render scene.ts --crop --out thumb.png        # cropped to content (cheap iteration)
sketchling render scene.ts --video out.mp4 --fps 30      # the whole timeline, as an MP4 (~1s longer than the timeline's own duration — it holds on the settled end frame)
sketchling render scene.ts --serve                       # open live in a real browser
```

Tier 0 lint (off-canvas, degenerate shapes, heavy overlap, off-center composition) runs on every render automatically, for free, before any pixel exists. The overlap check tells containment apart from collision: a small detail sitting almost entirely inside a much bigger shape (an eye on a face, a keyhole on a screen — one shape's area at least 3x the other's, the smaller one barely denting the bigger one's own area) reports at `info` level, not `warn`, since that's normal nesting, not two things fighting for the same space. Two comparable-sized shapes overlapping heavily still `warn` — that's the case actually worth a look. For a specific overlap you know is intentional and the size heuristic doesn't catch (layered mechanical rings of similar size, e.g.), call `.lintIgnore("overlap")` on either node to silence just that check on it.

### Primitives

- `sketch.stroke(points, style)` — an open freehand line
- `sketch.loop(points, style)` — a closed freehand shape
- `sketch.blob(cx, cy, radius, style, vertices?)` — an organic, deliberately-not-a-perfect-circle shape. `vertices` (default `10`) controls outline complexity. Below roughly 8-9px radius the outline jitter overwhelms the fill and small blobs stop reading clearly — give a "bubble" radius ≥9-10 and a light weight, not a tiny radius. The imperfection is baked into the authored points, not just render-time jitter (`looseness`, default `0.3`, perturbs the actual outline coordinates) — a clean-line/ligne-claire register (see `examples/gallery/ligne-claire-look.ts`) wants `looseness: 0` explicitly on every blob, or a window/head reads as hand-wobbled instead of precise. Note `looseness: 0` still isn't a perfect circle — the wobble floor (~15% of radius) doesn't reach zero; for an actually clean disc, use `sketch.ellipse()` instead.
- `sketch.ellipse(cx, cy, rx, ry, style, vertices?)` — a true, wobble-free ellipse (`rx === ry` for a circle), no seeded jitter at all in the authored geometry. `look: "ink"`'s own render-time sketchiness still applies on top like any other stroke; this only controls the underlying points. For a sun, a head, a gear hub, a glow ring, a star — anything meant to read as a clean disc rather than a hand-wobbled one. See `examples/gallery/ellipse-shapes.ts`.
- `sketch.group(children)` — groups nodes so they move/scale/rotate together. `.stagger(each, {duration, at, ease, effect})` choreographs children's entrances with rhythm.
- `sketch.text(str, x, y, style, {size?})` — hand-lettered text. Lowercase a-z, digits, basic punctuation (`. , ! ? ' -`); no case distinction. `size` is the approximate letter height in pixels (default `48`), not a raw scale multiplier. Returns a `Group` of one Stroke per letter-stroke — animate with `.stagger()` for a letter-by-letter reveal, or leave it static.
- `sketch.film({width, height, background})` — cuts several independent `Scene`s together (see Film below).
- `sketch.arrow(from, to, style, {headSize?, headAngle?})` — a shaft plus a two-stroke head, angled toward `to`. Thin composition, returns a `Group`.
- `sketch.speechBubble(x, y, width, height, style, {tailAt?, tailSize?})` — a rounded rectangle with a triangular tail (`tailAt`: `"bottom-left" | "bottom-center" | "bottom-right" | "top-left" | "top-center" | "top-right"`). One closed stroke.

`scene.add(node)`/`group.add(node)` return the node you just added, not the scene/group itself — that's what makes `scene.add(ground).drawOn({...})` a valid one-liner (assign-and-animate in the same expression, used constantly throughout this codebase), but it also means `.add(a).add(b)` does NOT chain the way a fluent builder API would: the second `.add` runs on `a` (whatever `.add()` just returned), not on the container, and fails outright since a plain node has no `.add` method. Add multiple children with separate statements, or build the array up front and pass it to `sketch.group(children)`'s own constructor.

All points are `[x, y]` pairs in the scene's own absolute canvas coordinates — draw shapes directly where they should appear.

### Style

`color`, `weight` (`"light" | "confident" | "bold"` or a number), `looseness` (0-1, precise → wild), `energy` (`"calm" | "quick" | "frantic"`), `smooth` (spline vs. straight edges — default `true`, use `false` for boxes/wedges needing sharp corners), `fill` (`{ color, style: "hachure" | "cross-hatch" | "solid" | "zigzag" | "dots", density, angle }`).

`fill.color` takes a gradient too — the same `{ stops: [{offset, color}], direction? }` shape `scene.background` already takes — for a real per-shape SVG gradient (`objectBoundingBox`-scaled, no need to know the shape's own pixel size) instead of a flat color: a landform lit from one side and falling into shadow, a body with a shaded underside, real volumetric shading on one form rather than a uniform fill. Only renders as an actual gradient with `fill.style: "solid"` (or under a look that forces solid — `"flat"`/`"clay"`; `texture` is a separate axis that doesn't affect fillStyle at all) — `"hachure"`/`"cross-hatch"`/`"zigzag"`/`"dots"` are procedural line strokes with no continuous area to gradient across, so a gradient color under those degrades to its first stop instead. Same for the SVG-sketched 3D mesh pipeline and a limb's cap color — no per-shape gradient concept there either, so those also just take the first stop. See `examples/gallery/gradient-shading.ts`. `sketch.shade(base, {from?, amount?})` derives that `{stops, direction}` shape from ONE base color instead of hand-picking stops — `from` (default `"top"`) picks which edge the light comes from, `amount` (default `0.35`) how strong the falloff is; a highlight → base → shadow spread, the shadow side nudged cool/blue-violet and the lit side warm rather than a flat lighter/darker lerp. `fill: { color: sketch.shade("#7a9e5f"), style: "solid" }` is a drop-in replacement for a flat color anywhere a gradient is valid. See `examples/gallery/shade-helper.ts`.

### Animation

Every node: `.drawOn({at, duration, ease})`, `.appear(...)`, `.moveTo(x, y, ...)`, `.moveBy(dx, dy, ...)`, `.scaleTo(s, ...)`, `.rotateTo(deg, ...)`, `.rotateBy(deg, ...)`, `.fadeTo(opacity, ...)`. `at` is an absolute position (seconds) on the scene's shared timeline.

- `drawOn`'s `duration` is optional — omitted, it scales with the path's own length.
- `moveTo(x, y)` is a true absolute position: the node's own geometric center ends up at canvas `(x, y)`, regardless of its current position. `moveBy(dx, dy)` is relative. Same pairing for rotation: `rotateTo(deg)` is an absolute target angle, `rotateBy(deg)` turns relative to whatever the node's rotation actually is when the tween starts playing — including mid-chain through an earlier `rotateTo`/`rotateBy` — so a repeated turn (a crank wound the same amount each time, a wheel that just keeps spinning) doesn't need its absolute target computed by hand from wherever the last turn left it.
- `.pivotAt(x, y)` (any node) anchors `rotateTo`/`rotateBy`/`scaleTo` at an absolute canvas point instead of the node's own center — needed for e.g. a limb that should swing from a joint, not its own midpoint. With no pivot set, a node rotates and scales about its own authored-geometry centre, which is usually what you want; reach for `pivotAt` when the anchor is somewhere else (a shoulder, a hinge, a contact point on the ground).
- **Instant, non-tweened state at a specific point on the timeline**: any animate call with `duration: 0` snaps immediately rather than interpolating — `scope.rotateTo(-10, { at: 4, duration: 0 })` sets the angle outright at t=4, no fake near-zero epsilon duration needed. `initial({...})` is the same idea but only for the very start of the timeline (t=0, before anything else runs); `duration: 0` on any op is the general form, for a snap at any `at`.
- `.morphTo(points, {at, duration, ease})` — a drawn stroke/loop/blob reshapes into new points instead of a new shape appearing (via GSAP's MorphSVGPlugin). Color/fill style stay the same, only geometry changes. Disables line-boil on that node (avoids a visible snap-back mid-morph). Not available on `Group`/`sketch.text()` nodes.
- `.drawOn()` only reveals `stroke`/`blob`/`loop` nodes and `sketch.text()` groups — a plain `Group` has no single path to trace, so `.drawOn()` on one is a no-op (validate/lint flags this). Use the Group's own `.stagger({ effect: "drawOn" })` to draw each child in sequence instead.
- A drawing doesn't have to go still once finished: chain `moveBy`/`rotateTo`/`scaleTo`/`fadeTo` after a `drawOn` window closes for motion that continues past the reveal. Optional, not an expectation.
- Two shapes drawing at once reads as two hands — sequential `drawOn` windows with a short gap is the default worth reaching for, but nothing prevents overlap when that's the actual effect wanted.
- The scene's actual rendered length is always derived from whatever the last op resolves to — there's no separate concept of "how long is this scene" that overrides that. `scene.duration(seconds)` doesn't change this; it declares the length you *intend*, purely so the linter can warn when some op is scheduled to end past it (an extrapolated off-screen element, a chain that runs one leg too long) — the kind of silent overrun otherwise only noticed by the rendered video being mysteriously longer than expected. Only checks ops with an explicit numeric `duration` (not `drawOn`'s auto-pace or `springTo`'s automatic settle window, neither knowable without rendering). Optional — a scene that never calls it behaves exactly as before.
- **Two tweens writing the same property on the same node over an overlapping window silently fight — the later-inserted one wins for as long as both run, with no error anywhere.** This is the single most common real bug this library produces at any real scale: a reusable idle-sway helper (a subtle continuous `rotateTo` loop) and a scene-specific "acting" `rotateTo` gesture both touching a character's rotation over the same span, or two `fadeTo` calls on the same particle (a fade-in still finishing when a flicker adjustment starts). The linter now catches this statically per property/axis — `x`/`y` (`moveTo`/`moveBy`/`moveAlong`), `rotation` (`rotateTo`/`rotateBy`), `scaleX`/`scaleY` (`scaleTo`/`squashTo` — `scale` is sugar for both under the hood, so they share the same bucket), `opacity` (`fadeTo`/`appear`) — and only within the SAME axis: a stride's `moveBy(dx, 0)` overlapping a bob's `moveBy(0, dy)` on the same node is the correct, intended composition (see `moveBy`'s own zero-axis-skip fix above) and does not warn, only two ops that actually touch the same axis do. Fix by staggering the windows, routing one through pivot/a wrapper group instead of the same property, or folding both into one call.
- Every already-drawn line keeps re-jittering a few times a second on its own — automatic, not something to configure.
- `.moveAlong(points, {at, duration, ease, rotate?})` — a curved path through `points` (GSAP MotionPathPlugin), not the straight segments a chain of `moveBy` would give. `rotate: true` faces the node into its direction of travel (off by default).
- `.squashTo(scaleX, scaleY, {at, duration, ease})` — non-uniform scale, the basic cartoon weight/impact cue (flatten on landing, stretch mid-jump, snap back). Unlike `scaleTo`, this is what makes motion read as having mass.
- **`moveTo`/`moveAlong` target the node's own bbox center by default, not necessarily the point you were thinking of when you built it.** A vertically lopsided shape (tall body, small feet) has a bbox center well away from the "obvious" reference point — animating a path authored at, say, the feet's height lands the shape floating or sinking if you leave the default in place. Both take an `anchor` option instead: `{ anchor: "top" | "bottom" | "left" | "right" }` targets that edge's own midpoint (`"bottom"` for feet), not a corner — `figure.moveTo(150, groundY, { anchor: "bottom" })` puts the feet exactly on `groundY` directly, no `intendedY - bboxCenterY` arithmetic worked out by hand first. Default (`"center"`, or the option omitted) is exactly today's behavior — nothing changes for existing scenes. Still worth rendering a mid-motion `--at` frame and checking before trusting a longer path, especially for `moveAlong`.

### Scheduling — labels and relative time, instead of a wall of hand-summed literals

Every independent stress test this library has had converged on the same complaint: past a handful of beats, a scene becomes a wall of hand-computed `at` literals (`// ends ~29.5 at x = 1252`) that silently go stale the moment anything upstream is retimed. Two tools fix this, and they solve different halves of the problem:

```ts
const scene = sketch.scene({ width: 480, height: 320 });
scene.label("liftoff", 2.5); // name a point on the shared timeline — declare it wherever, in any order

const rocket = sketch.stroke([[0, 0], [40, -40]]);
scene.add(rocket).moveTo(0, -40, { at: 0, duration: 1.5 });
scene.add(sketch.loop([[0, 0], [10, 0], [10, 10], [0, 10]], { smooth: false })) // exhaust puff
  .appear({ at: "liftoff+0.2", duration: 0.4 }); // a moment just after the named point, not a re-derived literal

const flag = sketch.loop([[0, 0], [20, 0], [20, 14], [0, 14]], { smooth: false });
scene.add(flag).drawOn({ at: 0, duration: 0.6 });
flag.fadeTo(0, { at: flag.endAt, duration: 0.3 }); // "right after whatever I just did", no manual sum
```

- **`scene.label(name, seconds)`** names a point on the scene's shared timeline. Reference it later as an `at` value: the plain name (`"liftoff"`), or with an offset (`"liftoff+0.4"` / `"liftoff-0.2"`, whitespace around the sign is fine). Every fluent animate call, and `scene.camera()`'s own `panTo`/`panBy`/`zoomTo`/`follow`, accept this anywhere a plain number works. Declare a label in any order relative to what references it — resolution happens once, at render time, after the whole scene has finished being authored, not as each call is made. An unknown label or a malformed reference (a typo) throws immediately with the bad name in the message, instead of silently resolving to `NaN` and producing a scene that's wrong with no error anywhere. This is for referencing one point in time from several different nodes/ops — the caption-tracks-the-camera-pan pattern, a mechanism whose several moving parts all key off one moment — where re-deriving the same literal in five places is exactly how they drift out of sync.
- **`node.endAt`** is the end time (seconds) of the most recently added animation on that node — `at + duration`, using the same default duration every op kind actually renders with when none is given explicitly (matching `renderer.ts`'s own fallbacks exactly), and a length-based estimate for an undecorated `drawOn` (see `polylineLengthDrawDuration` — an estimate, since the renderer measures the true on-screen path length via the browser, which core can't reach; close enough to chain off of, not a rendering guarantee). This is for continuing the SAME node's own sequence without hand-summing durations: `node.moveTo(...); node.rotateTo(..., { at: node.endAt, ... })` instead of tracking a running total by hand. Throws if the last op's own `at` is still an unresolved label reference (a string) — there's nothing concrete to add a duration to before that resolves, at render time. Empty animations list reads as 0.
- Both resolve to plain numbers before anything else sees them — the renderer, the linter, agent validation (`sketchling validate`) all operate on fully-resolved seconds exactly as before; neither `AnimOp` (the wire format) nor determinism are affected by any of this. A scene that never uses either behaves exactly as it always has.

### Camera — panning and zooming within a world bigger than the screen

```ts
const scene = sketch.scene({ width: 4200, height: 700, viewport: { width: 640, height: 440 }, background: "#f2d4a3" });
const cam = scene.camera();
cam.panTo(500, 400, { at: 0, duration: 0 });
cam.follow(someNode, { at: 2, duration: 6 }); // tracks someNode's live position, mid-tween included
cam.zoomTo(1.3, { at: 4, duration: 1 });       // independent of pan — both can run at once
```

`scene.camera()` returns `.panTo(x, y, opts)`, `.panBy(dx, dy, opts)`, `.zoomTo(scale, opts)`, `.follow(node, opts)` — same `{at, duration, ease}` as node animations. `panTo(x, y)` takes an ABSOLUTE scene-space point to center the viewport on, not a delta — a "barely-perceptible drift" authored as `panTo(6, -2, ...)` (intending a 6px/-2px nudge) instead sends the camera racing toward scene-space `(6, -2)`, nowhere near a 640×400 canvas's actual default center `(320, 200)`, dragging the whole frame off past the world's top-left corner by the end of the tween. Offset from the real center (`panTo(326, 198, ...)` for the example above), not from zero — or reach for `panBy(dx, dy, opts)` when the delta really is what you mean: it pans relative to wherever the camera's center actually is when the tween starts (including mid-follow, or after an earlier panTo/panBy), so a repeated small nudge doesn't need its absolute destination worked out by hand. Separately: keep the camera's own framing inside the world's bounds on every axis (`center ± viewport/2` within `[0, WORLD_W]`/`[0, WORLD_H]`) — letting the viewport extend past a world edge (a `follow` target ending up close enough to one, e.g.) shows bare `scene.background` where the depth-1 content has run out, reading as a stray pale rectangle (`quiet-ride.ts` hit this before it was root-caused: the backdrop sits at depth 0 and never pans, so once the frame extends past where the foreground actually reaches, what's left showing is just the still, unpanned background). The Tier 0 linter now catches this directly — a `panTo` that frames past the world's edge is a warning, not a silent artifact — but it's still worth keeping real margin (half the viewport's width/height) between wherever the camera ends up centered and every world edge. This is what gives continuity a Film cut can't: one continuous scene the camera moves through, instead of independent scenes where nothing can just *keep going* because every cut starts an unrelated Scene. Build once, travel through the world — don't rebuild the same thing at every stop. A scene that never calls `.camera()` renders exactly as before, at no cost.

`.follow` keeps tracking the node past its own `at+duration` — `duration` is when it starts being eligible to be superseded, not a hard cutoff. It stays in control until a later `panTo`/`zoomTo`/`follow` (a camera op whose own `at` comes after this follow started) actually takes over; with nothing scheduled after it, it holds the node's live position for the rest of the scene, including any settle/hold tail (particle dust, a spring settling) past the tracked node's own last motion. No need to pad `duration` defensively to avoid a snap — there isn't one.

**Parallax layers**: `scene.layer(depth, children?)` returns a `Group` pinned to a depth plane — when the camera pans, each layer moves by a fraction of that pan based on its depth (the 2D depth illusion, not literal 3D). `depth` 1 (default, no `.layer()` call needed) moves 1:1 with the camera; `<1` recedes (background), `>1` pops forward (foreground). Only visible alongside camera pan/follow; zoom applies uniformly. The scene's `background` always sits farthest back, behind every layer.

**Gradient backgrounds**: `background` takes a color string or `{ stops: [{offset, color}], direction?, type? }` — one real SVG gradient instead of hand-authoring band rectangles to fake one. `type` defaults to `"linear"` (today's behavior, `direction: "horizontal" | "vertical"` — an axis to run along). `type: "radial"` instead radiates from a center (`direction` is meaningless there and ignored) — centered on the scene itself for a background, reaching the farthest corner; centered on the shape's own bbox for a per-shape `fill.color` (see below), reaching every edge. The same shape works both places: a per-shape radial fill is the real fix for a light source's falloff (a candle, a lantern, a sun) — every one of this library's own examples that needed one faked it as several flat-colored ellipses stacked at decreasing alpha before this existed; a stop fading to a transparent color (`"#ffcf5c00"`, alpha `00`) reads as a soft glow dissolving into whatever's behind it, one fill instead of a handful of hand-tuned rings. See `examples/gallery/ellipse-shapes.ts`'s sun.

**3D**: `sketch.box3d(w, h, d, style)` / `sketch.icosahedron3d(radius, style)` / `sketch.mesh3d(vertices, faces, style)` (custom — `[x,y,z]` vertices, faces are `{indices, color?}` wound CCW from outside) return a node placed with the usual `moveTo`/`moveBy`. `.spin3d(rx, ry, rz, opts)` is an absolute-target rotation in degrees, chainable like `rotateTo`. Every face is rough.js-sketched and flat-shaded against a key light (`lightDir`, defaults upper-left); backface culling and painter's-algorithm depth sort run automatically every frame — only correct for non-intersecting geometry. A spinning mesh rebuilds its projected silhouette every tick (costlier than a static 2D shape), so reach for it where rotation is the point, not as a default upgrade.

**IK limbs and walking**: `sketch.limb(rootX, rootY, len1, len2, style, {bend, capRadius, capColor})` is a 2-bone chain (leg/arm) whose joint angle is solved every frame from an end-effector target — `.ikTo(x, y, opts)` moves that target (absolute, local space), instead of hand-authoring a rotateTo per segment. Give `len1+len2` real headroom over the distance it needs to reach (a chain at full extension gets its target silently clamped, which reads as a subtle pop, or — for a target well past reach — a rigid "plank arm" that never bends at all) — the linter now catches this statically (root and `ikTo` target are both known at build time) and names the actual overage in pixels, instead of only being visible once rendered. `sketch.walk({body, legs: [{limb, hipX}, {limb, hipX}], steps, stepLength, groundY, stepDuration?, liftHeight?, bodyBob?, at?, arms?: [{node, swingAngle?}, {node, swingAngle?}]})` generates a full bipedal gait — foot planting, lift-and-swing, body bob — over two limbs; returns `{endAt}` to chain what follows. `arms` (optional) adds a phase-locked contralateral counter-swing — `arms[0]` pairs with `legs[0]` as the SAME side and swings OPPOSITE that leg's own phase (right leg forward ↔ left arm forward, a real gait's cross pattern), `swingAngle` (default 16°) how far off rest. `node` can be any node with its own `.rotateTo` (a `Limb`, or a plain stroke/group swung as a rigid piece) — YOU must `.pivotAt()` it at the shoulder before passing it in, gait.ts doesn't know the arm's own local geometry, and an un-pivoted arm rotates around its own bbox center instead of the joint and visibly detaches (see `examples/gallery/walk-cycle-arms.ts`, `walk-cycle.ts`'s exact character with working arm swing added).

`sketch.quickRig(body, {groundY, stepLength?, hipDrop?, hipSpread?, reachMargin?, legStyle?, capRadius?})` auto-derives a headroom-safe two-legged rig from `body`'s own bounding box (a `Stroke`/`Blob`/`Group`) instead of hand-picking hip coordinates and leg lengths — the worst-case-reach math (`sqrt(stepLength² + hipToGroundDrop²)` sized with `reachMargin`, default `1.35`, i.e. 35% headroom) done automatically instead of by hand. Returns `{legL, legR, hipY, hipLX, hipRX, len1, len2}` — pass `legL`/`legR` straight into `sketch.walk`'s `legs` array. Named honestly: derives proportions from a bounding box (center, width, bottom edge), not a real skeleton pulled from an arbitrary drawn silhouette — good for a round or roughly-humanoid body, not a substitute for hand-placed `sketch.limb` joints on an unusual shape. See `examples/gallery/quickrig-walk.ts`, the same character as `walk-cycle.ts` with one `quickRig` call replacing five hand-picked constants.

**Secondary motion**: `node.springTo(driver, {offset?, stiffness?, damping?, at?})` makes `node` chase `driver`'s live position (plus a fixed `[dx,dy]` offset) with damped-spring lag and overshoot, instead of a hand-authored delay — a trailing bead, a bobble, anything reacting to what another node does. `stiffness` (default 120) higher = snappier; `damping` (default 12) higher = less overshoot (`2*sqrt(stiffness)` is critically damped, no overshoot). Runs from `at` (default 0) to the end of the timeline; precomputed once per scene build (a dense forward scan of the driver's own resolved position, integrated offline into a lookup table) rather than evaluated live, so seeking anywhere stays exact and repeatable like every other animation here — but that also means it isn't itself a tl.to() call, so a spring reserves its own settle time on the timeline automatically (roughly `9.2/damping` seconds after whatever else is happening ends) rather than needing one authored by hand. `springTo` alone only moves one node's own position — pair it with `sketch.connector(anchor, target, style)` to actually attach it to something: a connector is a stroke that rebuilds itself every seek from a fixed `anchor` point to `target`'s own live resolved position, bowed through one synthetic offset midpoint (not a straight segment) so it reads as a flexible rod bending under the tip's motion, not a rigid rotating stick. Together they make an actual bendy ear/antenna/tail — `target` doesn't have to be springing (a connector will track any node's live position), but that's the common pairing; see `examples/gallery/bendy-antenna.ts`. The same pairing is the fix for "hand-held prop motion reads rigid" (a fishing rod, anything a character holds and casts/swings): a fixed-ease `rotateTo`/`moveTo` that arrives and stops dead has no follow-through, so pair a snap-and-overshoot ease (`"back.out(n)"`, not `"sine.inOut"`) on the swing itself with a `springTo`'d prop and a `connector` line to it — see `examples/gallery/fishing-cast.ts`. No `drawOn` on a connector (there's no stable path length to reveal against geometry that changes every frame) and no line-boil (it already fully rebuilds each seek); `fadeTo`/`moveTo`/etc. on its own transform still work normally. Both `connector` and `springTo` read only a node's own local offset — a `target`/`driver` whose motion comes entirely from an animated ancestor group (e.g. a body placed inside a `sketch.walk` character) reads as stationary; give it its own tween if it needs to be tracked or spring-driven.

**Particles**: `sketch.particles(x, y, style, {count?, angle?, spread?, speedMin?, speedMax?, gravity?, lifetime?, duration?, at?, sizeMin?, sizeMax?, fade?, shape?, moveTo?})` — `count` (default 24) small dots launched from `(x, y)` within a cone (`angle` ± `spread`/2, degrees, screen convention 0 = +x/right, 90 = +y/down, default `angle: -90` = straight up), each under constant `gravity` (px/sec², default 220, pulls toward +y) — sparks, dust, confetti, snow, a firework burst. `duration` (default 0) spreads emission across a window instead of one burst; `lifetime` (default 1.2s) is how long each particle stays visible before disappearing, with `fade` (default true) ramping opacity in then out over it. Deliberately not a simulation: every particle's spawn time/launch angle/speed/size is drawn once from a seeded PRNG at build time, so its position at any t is a closed-form ballistic formula — `x0 + vx*age, y0 + vy*age + 0.5*gravity*age²` — with no history and no dependency on any other node, unlike `springTo`. That means no precomputed lookup table is needed at all (unlike springs, which genuinely require one) — an arbitrary seek is exact for free, the same way a plain `moveTo` tween already is. One real gotcha worth knowing: since a particle's motion is never itself a `tl.to()` call, nothing naturally extends the timeline to cover it — this reserves duration through the latest particle's own `spawnTime + lifetime` automatically, the same "compute after everything else is on the timeline" fix `springTo`'s settle-window needed (a real bug caught during development: a `--video` export rendered exactly one frame at t=0 before this was added, since `tl.duration()` was still 0 with nothing else on an otherwise-empty scene's timeline). See `examples/gallery/particle-burst.ts`.

`shape` (default `"dot"`) can be `"streak"` instead — a short line oriented along each particle's own instantaneous velocity (recomputed every seek as gravity bends it, so a falling streak visibly arcs, not frozen at its launch angle), for rain/sparks/debris — a round dot moving fast still reads as a dot, not motion. `moveTo: {x, y, duration, ease?}` moves the emitter's own spawn point in a straight eased line from `(x, y)` (the constructor's own spawn point) to `{x, y}` over `duration` seconds, for particles emitted from something moving (dust trailing a sailer, sparks off a rising rocket) without re-authoring that same motion tween a second time on the particles node. Resolved once per particle at its own spawn time, not "now" — a plain eased lerp, evaluable at any point since both endpoints and the duration are fixed at build time, so a particle launched early correctly trails behind where the source WAS then, rather than the whole cloud rigidly snapping to the source's current position every frame (which is what a live per-frame position read, the mechanism `camera.follow`/`springTo` use, would give you instead — wrong for a trail). See `examples/gallery/particle-streak-follow.ts`.

**Audio**: `sketch.sound(pitch, {at?, duration?, instrument?, velocity?, pan?})` — one scheduled note or hit, on the same scene-global `at` timeline every visual animation already uses. `pitch` is scientific pitch notation (`"C4"` = middle C), a raw MIDI number, or `null` for an unpitched percussive hit. `instrument` names a voice: `"piano"`/`"strings"`/`"pad"` are melodic, `"pluck"`/`"thud"`/`"brush"` are percussive/effect (default `"piano"`). `velocity` (0–1, default 0.8) scales loudness (non-linearly — closer to how loudness is actually perceived than a flat multiply); `pan` (-1..1, default 0) is stereo position. Every voice is synthesized (oscillators/noise + envelopes, see `render/audio.ts`) — sketchling doesn't bundle audio samples any more than it bundles pre-drawn shapes; `"piano"`/`"strings"` are an honest synthesized *approximation* of those timbres (closer to an electric piano and a bowed pad than a recording), not a claim of real-instrument fidelity — that tradeoff is deliberate, the same "primitives, not a curated asset library" boundary the visual side draws. No chord/melody/mood helper on top: a chord is several `sketch.sound()` calls at the same `at`, composing them is the caller's job.

Rendered offline via `OfflineAudioContext` inside the same browser page everything else renders from, muxed into `--video` output via ffmpeg (`-c:a aac`) — a scene with no `sketch.sound()` nodes renders exactly as before (no audio track added), so every existing silent example is unaffected. A `sketch.sound()` is never itself a `tl.to()` call, so (same fix `springTo`/`particles` needed for the same reason) it reserves timeline duration through its own `at + duration` automatically. The synthesized content is fully seeded/deterministic (same notes, same timing, same envelopes, every render) but NOT bit-exact reproducible — Chromium's own `OfflineAudioContext` isn't guaranteed bit-identical across runs (internal SIMD/summation-order differences); measured directly, ~0.01% of samples differ by exactly ±1 on a 16-bit scale, sub-perceptual rounding noise, not a different performance. Not yet wired: live playback under `--serve` (only `--video` export produces audio right now), and `"lit3d"`/`"toon3d"` scenes (a genuinely separate WebGL pipeline that doesn't collect sound events yet — a mesh3d scene with `sketch.sound()` in it renders silently rather than failing). See `examples/gallery/sound-motif.ts`.

Inside a `Film`, a `transition: "fade"` entry's own sound automatically gain-ramps through the same crossfade window its visuals already fade across — the outgoing scene's sound ramps 1→0 and the incoming scene's ramps 0→1, both over `[enterAt, enterAt + transitionDuration]`, instead of both playing at full authored volume through the overlap (which read as a louder-than-either-scene overlap with an audible pop at the cut). Automatic — no authoring needed beyond `transition: "fade"` itself; a `"cut"` transition keeps today's flat-gain behavior on both sides (nothing to crossfade against). Still a stretch goal, not yet built: one continuous film-level audio track/theme that survives cuts unbroken — every sound today is still authored per-scene.

`examples/showcase/` composes these together rather than demonstrating one at a time — `critter-hop.ts` (springTo + connector + particles), `quickrig-parade.ts` (quickRig + walk + camera.follow + particles), `toon-tumble.ts` (toon3d + squashTo choreography), `fireworks-finale.ts` (particles alone, six concurrent emitters), `rocket-launch-clean-line.ts` (a clean-line/ligne-claire story beat: walk-up, ignition, camera-followed liftoff), `rocket-launch-clean-line-film.ts` (the same register at full film scale — four `sketch.scene()`s cut together with `sketch.film()` and crossfades, plus a `sketch.sound()` motif spanning all four), `nightfall-hill.ts` (the densest single scene in the repo — 5-plane `scene.layer()` parallax, gradient-shaded landforms, a fully rigged original character, fireflies, wind-driven grass via connector+springTo, a 4-voice sound bed), `quiet-crossing.ts` (the deliberate opposite of `nightfall-hill.ts` — restraint over density: one small solid-silhouette figure, no face, naturalistic proportions, a slow sine-eased gait with no `squashTo`, walking past one bare branch-strokes tree under a huge dusk-gradient sky; `look: "ink"` + `texture: "grain"` picked over `"flat"` alone or `texture: "watercolor"` after comparing all three as stills of the same composition — density alone doesn't read as a storybook/illustration register, restraint does). `quiet-ride.ts` (a cyclist companion — same restraint, a world 3x the viewport wide so `camera.follow()` has to move a depth-0.45 background layer, not just translate one figure; surfaced the camera/world-bounds gotcha above — a stray pale rectangle once the viewport extended past the world's edge, now root-caused as the still depth-0 backdrop showing through and caught directly by the Tier 0 linter). Worth reading before building a similarly composed scene: `quickrig-parade.ts`'s own comment walks through deriving footfall dust positions from `gait.ts`'s own step math instead of trying to track a walking character's child nodes live, and both `critter-hop.ts` and `quickrig-parade.ts` document why their dust is precomputed rather than connector/springTo-tracked (see Secondary motion above).

### Look and texture — two independent axes

`sketch.scene({..., look: "ink" | "flat" | "clay" | "lit3d" | "toon3d", texture?: "watercolor" | "grain" | "pixel" })` — the same authored scene (geometry, physics, timing) painted differently. `look` controls the GEOMETRY treatment (how paths/fills/timing are computed); `texture` is an OPTIONAL whole-frame post-process layered on top, freely combinable with any of `"ink"`/`"flat"`/`"clay"` — a watercolor wash over ink's own sketchy jitter, or grain over flat's crisp precision, are both real and equally valid. This wasn't always two axes: an earlier revision folded watercolor/grain/pixel into `look` itself, forcing them to share flat's crisp geometry — workable until grain (aged paper) needed to pair with ink's hachure fills for an old-book/engraving register, and crisp-only broke that combination outright. Split into two fields instead of guessing at more special-cased look values.

`look` values — `"ink"` (default): hand-drawn treatment, sketchy jitter, line boil, a visible pen tip during drawOn. `"flat"`: crisp and precise instead — no jitter, no boil, solid fills, no pen tip. `"clay"`: subtler hand-molded jitter than ink, solid fills, and time itself quantized to a ~10fps hold (genuine stop-motion stepping, not a continuous tween). `"lit3d"`: a genuinely separate pipeline (WebGL/Three.js, not SVG/rough.js) — real directional + ambient lighting and cast shadows, driven by the same spin3d/moveTo/moveBy/scaleTo/squashTo ops. Only `mesh3d` nodes have a 3D representation; every 2D-only node (stroke, blob, limb, text) in the same scene simply doesn't render in `"lit3d"`. Lit real-time 3D, not a path tracer — call it that, not "photorealistic." `texture` doesn't apply here — a separate pipeline the 2D filter system doesn't reach. `"toon3d"`: `"lit3d"`'s exact pipeline — same camera, same lights, same shadows, same `mesh3d`-only scope — with `MeshToonMaterial` and a 4-step gradient map on each mesh instead of a continuous PBR response, for flat cel-shaded bands, plus a black inverted-hull outline (a second back-face-only mesh per object, scaled up ~4% and parented to the real mesh so it inherits every animated transform for free, no separate GSAP tween). A shading variant of `"lit3d"`, not a third pipeline; since every `mesh3d` face is already flat-shaded (uniform per-face normals, not smoothly interpolated), the banding shows as a difference in which of the 4 steps each face's brightness lands on relative to `"lit3d"`'s continuous value, not a gradient-within-a-face — real and verified (pixel-diff against the same scene under `"lit3d"` comes back well above noise), but subtler than cel-shading on smooth geometry would look, since this library's meshes are all low-poly and flat-shaded to begin with. The outline is what actually sells it as "toon," not the banding alone.

`texture` values — `"watercolor"`: a whole-frame SVG filter (turbulence displacement + blur) bleeding every edge, like wet pigment, over whichever `look` geometry is active. `"grain"`: a different whole-frame SVG filter aimed at a different target — feTurbulence noise converted to a pure-black layer whose alpha (not color) varies with noise brightness, blended over the source via `feBlend` `"overlay"` (darkens shadows/lightens highlights slightly, the way real grain modulates an image, not a flat semi-transparent layer on top) — fine aged-paper/film-grain texture instead of wet-media bleed. `"pixel"`: a raster post-process on every captured frame instead (downsample, then nearest-neighbor upscale — applied in `cli.ts` after the browser screenshot, via `ffmpeg`, not a DOM/SVG change) for blocky low-res cells; the only texture that needs `ffmpeg` on `PATH` outside of `--video`. Lives entirely in the CLI's capture step operating on the final composited frame, so unlike watercolor/grain (SVG filters scoped to each scene's own content, which DO apply correctly inside a `Film`) it stays scene-only — a `Film` entry using it doesn't get pixelated, since there's no way to selectively pixelate one entry's screen region after everything's already composited into one canvas — and invisible under `--serve` (which skips the capture step and opens the raw page).

One authored scene, not a rewrite, to switch either axis.

### Film — cutting scenes together

```ts
const film = sketch.film({ width: 640, height: 480, background: "#111" });
film.addScene(sceneA, { transition: "cut", hold: 0.4 });
film.addScene(sceneB, { transition: "fade", transitionDuration: 0.5, hold: 0.4 });
export default film; // renders/lints/videos exactly like a Scene
```

Each scene keeps its own size, background, and animation, fully independent — `Film` scales/centers each into a shared canvas (against that scene's own OUTPUT FRAME — `viewportWidth`/`viewportHeight`, not its world `width`/`height`, so a scene using `scene.camera()` inside a wider world composes at the right size instead of shrinking by however much bigger its world is than its own viewport) and sequences them, clipping each to that same frame so a camera-panned scene doesn't spill content past its intended bounds. No shared runtime state between scenes; a recurring character across a longer sequence needs its own shared builder function reused across scene files (see `examples/story/_shared.ts`).

### Things that look like bugs but aren't

- Tier 0's containment note (`info` level) on shapes nested on purpose (an eye inside a head) — expected, not a problem. A remaining `warn`-level overlap between two comparable-sized shapes is worth an actual look, or `.lintIgnore("overlap")` if you're sure it's intentional.
- A `--video` render running ~1s past the scene's own `totalDuration` — the settled-frame hold, not a bug.
- An element that's within `width`/`height` but never visible, in a scene using `camera()` — lint checks the world, not wherever the camera happens to be framed at a given moment. Work out roughly where the camera actually is when an element should be seen before assuming its placement is right.
- Tier 0's "renders fully off-canvas" (error level, not just a warning) on a `springTo` driver node parked off-world on purpose (transparent fill/stroke, radius ~1, never meant to be seen) — it's an invisible physics anchor, not a shape that should be visible.

### Verifying your own work

Render a still at a genuinely mid-motion timestamp (`--at 0.3`, not just the settled end state) before trusting an animation looks right. `--crop` gives a cheap, small image for fast iteration.
